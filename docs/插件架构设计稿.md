# ycIDE 插件架构设计稿（草案 v0.1）

> 状态：草案 v0.4，§13 中的问题已全部拍板，见 §13.1。
> 目标读者：ycIDE 维护者与核心贡献者。

---

## 0. 目标与非目标

### 目标
1. **一切皆插件**：编辑器、渲染后端、语言服务、编译器、AI、调试器、支持库、主题都以插件形式存在，宿主只提供最小内核。
2. **插件与宿主框架解耦**：插件边界是**进程间协议**（JSON-RPC），不绑定 Electron / React。宿主继续使用 Electron（§13.1 第 2 条）；协议保持与框架无关，将来如果触发重新评估条件需要换成原生宿主，服务插件和数据插件不用重写。
3. **渲染可替换**：表格代码与流程线的渲染做成独立的渲染后端插件，先提供 DOM 和 Canvas(WebGL) 两种。
4. **渐进迁移**：每个阶段都能正常发版，不做停摆式重写。

### 非目标（本稿不处理）
- 插件市场的商业化、会员体系。
- 编译器内部（`transpileEycContent` / `generateMainC`）的细粒度重构。编译器先整体作为一个插件。
- 原生宿主。已决定继续使用 Electron，原生宿主只在满足 §13.1 第 2 条的触发条件时重新评估。

## 1. 设计原则

| 原则 | 含义 |
|---|---|
| **宿主拥有状态** | 文档内容、版本号、项目结构、设置、密钥都由宿主保管；插件只能通过协议读写。这样多个插件（编辑器、AI、调试器）看到的是同一份文档，不会各存一份。 |
| **协议优先** | 所有能力先定义成协议消息，再在 Electron 里实现。禁止插件直接调用 `window.api` 或 Electron 模块。 |
| **声明式贡献** | 插件在清单（`plugin.json`）里声明自己贡献了什么（命令、菜单、编辑器、工具……），宿主不加载代码就能建菜单、建索引，按需激活。 |
| **数据插件零代码** | 主题、支持库元数据、图标包这类插件只有数据文件，没有可执行代码。 |
| **可撤销** | 插件注册的一切（命令、视图、事件监听、装饰）都返回 disposable，停用插件时宿主统一回收，支持热卸载。 |
| **最小权限** | 插件在清单里声明权限，第三方插件跑在独立进程里，越权调用由宿主拒绝。 |
| **复用成熟协议** | 语言服务参考 LSP，调试参考 DAP，不自己发明不必要的东西。 |

## 2. 总体架构

```
┌──────────────────────────────── 宿主 Host ────────────────────────────────┐
│                                                                           │
│  内核服务：插件管理 · 命令注册表 · 文档仓库 · 项目/工作区 · 设置 · 密钥    │
│            事件总线 · 权限检查 · 布局/视图容器 · 日志                       │
│                                                                           │
│  UI 外壳：标题栏 / 工具栏 / 侧边栏 / 编辑区 / 底部面板 / 状态栏（只是容器） │
│                                                                           │
└──────┬──────────────────────┬───────────────────────┬─────────────────────┘
       │ JSON-RPC             │ JSON-RPC              │ 视图协议
       │ (stdio/管道)         │ (MessagePort)         │ (iframe/原生子区域)
┌──────▼───────┐   ┌──────────▼──────────┐   ┌────────▼─────────────────┐
│ 服务插件进程  │   │ 插件宿主进程(Node)   │   │ UI 插件                   │
│ 原生 exe 等   │   │ 运行多个 JS 插件     │   │ 编辑器 / 视图 / 渲染后端   │
│ 例：编译器    │   │ 例：AI、语言服务     │   │ 例：表格编辑器、窗口设计器 │
└──────────────┘   └─────────────────────┘   └──────────────────────────┘

数据插件（主题、支持库、图标）：没有进程，宿主直接读取清单与文件。
```

### 2.1 插件的三种形态

| 形态 | 有无代码 | 运行位置 | 典型例子 |
|---|---|---|---|
| **数据插件** | 无 | 宿主直接读取 | 主题、支持库（命令清单 + C++ 实现源码）、图标包 |
| **服务插件** | 有，无 UI | 独立进程（Node 插件宿主进程，或任意语言的可执行文件） | 编译器、语言服务、AI 模型提供方、AI Agent、调试适配器、易语言项目导入 |
| **UI 插件** | 有，带 UI | 宿主的视图容器里（Electron：iframe / webview；原生宿主：原生子区域或嵌入 WebView2） | 表格编辑器、流程线/表格渲染后端、窗口设计器、AI 对话面板、终端 |

一个插件包可以同时包含服务部分和 UI 部分（例如 AI 插件 = 服务端模型调用 + 对话面板 UI），两部分之间也通过协议通信。

### 2.2 进程模型

| 进程 | 内容 | 隔离级别 |
|---|---|---|
| 宿主主进程 | 内核服务、插件管理、窗口 | — |
| 宿主 UI 进程 | 外壳 UI、视图容器 | — |
| 内置插件宿主进程 | 所有**官方内置**的 JS 服务插件共用一个 Node 进程 | 低（信任） |
| 第三方插件宿主进程 | 第三方 JS 服务插件，每个发布者一个进程 | 高（权限受限） |
| 独立服务进程 | 声明 `runtime: "executable"` 的插件（例如原生编译器、调试适配器） | 由清单权限约束 |
| 编译工作进程 | 编译器插件自行管理（沿用现有 compile-worker） | — |

插件进程崩溃时宿主负责重启（指数退避，3 次失败后停用并提示），不影响其他插件。

## 3. 插件包与清单

### 3.1 目录结构

```
<插件id>/
  plugin.json          # 必需：插件清单
  dist/                # 服务端代码（JS）或可执行文件
  ui/                  # UI 部分（HTML/JS 或原生 DLL）
  data/                # 数据文件（主题、命令清单等）
  README.md
  CHANGELOG.md
```

安装位置：
- 内置插件：`<安装目录>/plugins/`，随 ycIDE 发布，只读。
- 用户插件：`<userData>/plugins/`。
- 开发中插件：环境变量 `YCIDE_EXTRA_PLUGIN_DIRS` 指定的目录（多个用系统路径分隔符隔开），改完代码用「工具 → 重新加载插件」生效；后续再加到设置里。

### 3.2 `plugin.json` 示例

```jsonc
{
  "id": "ycide.ai.deepseek",              // 全局唯一，发布者.名称
  "displayName": "DeepSeek 模型",
  "version": "1.2.0",                      // semver
  "publisher": "ycide",
  "engines": { "ycide": ">=0.1.0", "protocol": "1.x" },
  "description": "为 AI 助手提供 DeepSeek 模型接入。",

  "platforms": ["windows", "linux", "macos"],  // 可加载的宿主平台，见 §3.4；省略表示全平台
  "hosts": ["electron", "native"],             // 可加载的宿主类型；省略表示全部

  "runtime": {                             // 没有代码的数据插件省略整个 runtime
    "type": "node",                        // node | executable | none
    "main": "dist/index.js"
    // type=executable 时按平台给出可执行文件，见 §3.4：
    // "command": { "windows-x64": "bin/win-x64/xxx.exe", "linux-x64": "bin/linux-x64/xxx" }
  },

  "activationEvents": [                    // 何时启动插件进程（懒加载）
    "onAIProvider:deepseek"
  ],

  "permissions": [                         // 见 §8
    "net:api.deepseek.com",
    "secrets:own"
  ],

  "dependencies": {                        // 依赖的其他插件
    "ycide.ai.core": "^1.0.0"
  },

  "contributes": {                         // 贡献点，见 §6
    "aiProviders": [
      { "id": "deepseek", "label": "DeepSeek V4 Pro", "models": ["deepseek-v4-pro", "deepseek-v4-flash"] }
    ],
    "settings": [
      { "key": "deepseek.apiKey", "type": "secret", "title": "API Key" }
    ]
  }
}
```

### 3.3 激活事件

| 事件 | 触发时机 |
|---|---|
| `onStartup` | 宿主启动后（尽量少用，影响启动速度） |
| `onLanguage:<语言id>` | 打开某种语言的文档 |
| `onFile:<glob>` | 打开匹配的文件，例如 `onFile:*.efw` |
| `onCommand:<命令id>` | 执行某个命令 |
| `onView:<视图id>` | 打开某个视图 |
| `onAIProvider:<id>` / `onAITool:<名称>` | 选用某个模型 / AI 调用某个工具 |
| `onCompile:<目标>` | 发起编译 |
| `onDebug:<类型>` | 启动调试 |

### 3.4 平台标签

ycIDE 本身要跨平台运行，插件必须声明自己能在哪些平台上加载。这里要区分两个概念：

| 概念 | 字段 | 含义 | 例子 |
|---|---|---|---|
| **宿主平台** | `platforms` | ycIDE 运行在哪个系统上时可以**加载**这个插件 | D2D 渲染后端只能 `["windows"]`；Linux 上的 ycIDE 不加载它 |
| **目标平台** | `targets`（编译器、支持库专用） | 编译出来的程序运行在哪个系统上 | WebView2 支持库只有 Windows 实现，`targets: ["windows"]` |

规则：
1. `platforms` 取值为 `windows` / `linux` / `macos`，可以加架构后缀精确到 `windows-x64`、`linux-arm64`。省略表示全平台。
2. 宿主启动时先按 `platforms` 和 `hosts` 过滤：不匹配的插件**不加载、不激活**，在插件管理界面显示为「当前平台不可用」，并说明原因。
3. 商店只给当前平台展示可安装的插件；手动安装不匹配的插件时拒绝安装。
4. `runtime.type = "executable"` 的插件必须按平台提供可执行文件（`command` 为「平台 → 路径」的映射），当前平台没有对应文件即视为不可用。
5. 支持库的「宿主平台」和「目标平台」是分开的：在 Linux 上的 ycIDE 里交叉编译 Windows 程序时，只有 Windows 实现的支持库**照样加载**，但它的命令只在编译目标为 Windows 时出现在补全和编译里。这和现在 `libraryManager.getAllCommands(targetPlatform)` 按目标平台过滤的行为一致。
6. 依赖关系也要满足平台：插件 A 依赖插件 B，而 B 在当前平台不可用，则 A 也不加载。

## 4. 通信协议

### 4.1 传输层
- 消息格式：**JSON-RPC 2.0**。
- 传输方式：
  - Node 插件宿主进程：Electron `utilityProcess` + `MessagePort`。
  - 可执行文件插件：stdio，按 LSP 的 `Content-Length` 头分帧。
  - UI 插件：`postMessage`（iframe）或原生宿主提供的通道。
- 大数据（图片资源、编译产物）**不走消息体**：传文件路径或宿主分配的临时句柄，避免大块 base64。

### 4.2 生命周期

```
宿主                                插件
 │── initialize(宿主信息, 能力) ───▶│
 │◀──────── 结果(插件能力) ─────────│
 │── initialized ──────────────────▶│   插件此时可以注册命令、订阅事件
 │            ……正常工作……          │
 │── shutdown ─────────────────────▶│   插件释放资源
 │◀──────── 结果 ───────────────────│
 │── exit ─────────────────────────▶│
```

`initialize` 里双方交换协议版本和能力列表，宿主据此决定开放哪些接口。协议主版本不一致时拒绝加载并提示。

### 4.3 通用约定

| 约定 | 说明 |
|---|---|
| 命名 | `命名空间/方法`，例如 `workspace/readFile`、`compiler/build` |
| 取消 | `$/cancelRequest { id }`（同 LSP） |
| 进度 | `$/progress { token, value }`，用于编译、AI 流式输出 |
| 流式输出 | 请求带 `partialResultToken`，结果分片通过 `$/progress` 推送 |
| 错误码 | 沿用 JSON-RPC 标准码，自定义码从 `-33000` 开始：`-33001` 无权限、`-33002` 文档版本过期、`-33003` 插件未激活、`-33004` 用户取消 |
| 超时 | 请求默认 30 秒，编译、AI 等长任务通过进度消息保活 |

## 5. 宿主核心服务（插件可调用）

这些是插件 → 宿主的接口，替代现在 preload 里的 `window.api`。

| 命名空间 | 主要方法 | 对应现状 |
|---|---|---|
| `commands` | `register`、`execute`、`getAll` | `App.tsx` 的 `handleMenuAction` 大 switch |
| `workspace` | `getProject`、`readFile`、`writeFile`、`listFiles`、`watch`、`onDidChangeFiles` | `project:*`、`file:*` IPC |
| `documents` | `open`、`get(uri)`、`applyEdit(uri, version, edits)`、`onDidChange`、`onDidSave` | 现在分散在 `Editor.tsx` 的 tab 状态里 |
| `window` | `showMessage`、`showQuickPick`、`showInputBox`、`showConfirm`、`openView`、`setStatusBarItem` | `dialog:*`、各组件自己弹的对话框 |
| `settings` | `get`、`update`、`onDidChange` | `settings:*` |
| `secrets` | `get`、`store`、`delete`（只能访问本插件自己的密钥） | 主进程 `safeStorage` 加密的 API Key |
| `output` | `createChannel`、`append`、`clear` | `compiler:output` 等推送 |
| `diagnostics` | `set(uri, problems)`、`clear` | 编辑器诊断 + 编译错误 |
| `decorations` | `set(uri, 类型, 范围列表)`、`clear` | 断点、调试当前行、AI diff 高亮（现在通过 props 传给表格编辑器） |
| `terminal` | `create`、`send`、`read`、`onData` | `terminal:*` |
| `events` | `emit`、`on`（插件间自定义事件） | — |
| `plugins` | `getExtension(id)`、`getApi(id)`（获取其他插件导出的接口） | — |

### 5.1 文档仓库（关键设计）
- 每个打开的文档有 `uri` + 单调递增的 `version`。
- 所有修改都通过 `documents/applyEdit` 提交，带上基于哪个版本修改；版本过期返回 `-33002`，由插件重新获取后再提交。
- 编辑操作是**文本层面的编辑**（行列范围 + 新文本）。表格编辑器内部用表格模型，但对外提交时换算成文本编辑。这样 AI 改代码、格式化、重构、撤销栈都在同一套机制下工作。
- 撤销/重做由宿主统一管理（跨编辑器、跨 AI 修改），解决现在 `onGlobalUndo/onGlobalRedo` 需要层层传递的问题。

## 6. 贡献点（Contribution Points）

### 6.1 命令、菜单、快捷键

> 阶段 0 已实现（`src/shared/plugin/`，内置插件清单在 `src/plugins/*/plugin.json`）。下面的格式即实际实现的格式。

```jsonc
"contributes": {
  "menubarMenus": [                                   // 顶层菜单，按 order 从左到右
    { "id": "build", "title": "编译", "mnemonic": "B", "order": 50 }
  ],
  "commands": [                                       // 命令 ID 用「分类:名称」
    { "id": "build:compile", "title": "普通编译", "enablement": "projectOpen" }
  ],
  "menus": {
    "menubar/build": [                                // 可以往其他插件声明的顶层菜单里加项
      { "command": "build:compile", "mnemonic": "C", "group": "1_compile@1" },
      { "submenu": "ycide.recentOpened", "title": "最近打开", "group": "2_open@4" }  // 动态子菜单，由宿主填充
    ]
  },
  "keybindings": [
    { "command": "build:compile", "key": "CmdOrCtrl+F7" },
    { "command": "edit:undo", "key": "CmdOrCtrl+Z", "when": "!editableFocus" },
    { "command": "edit:redo", "key": "CmdOrCtrl+Y", "mac": "CmdOrCtrl+Shift+Z" },
    { "command": "file:exit", "key": "Alt+F4", "mac": "CmdOrCtrl+Q", "dispatch": false }
  ]
}
```

- 菜单项按 `group` 的组名排序，组之间自动插入分隔线；`@序号` 决定组内顺序。
- 命令的 `enablement` 不满足时菜单项置灰；菜单项的 `when` 不满足时不显示。
- 快捷键按声明顺序匹配，修饰键必须完全一致（`CmdOrCtrl` 接受 Ctrl 或 Cmd）；`mac` / `win` / `linux` 覆盖默认按键，`platforms` 限定生效平台。
- `dispatch: false` 的绑定只用于菜单显示与 macOS 原生菜单加速键，按键实际由系统、编辑器或其他绑定处理（如 Alt+F4、Delete、全选）。
- `when` 表达式基于宿主维护的上下文键。阶段 0 已有：`projectOpen`、`workspaceOpen`、`fileOpen`（菜单状态），`editableFocus`、`nativeTextSelection`（快捷键分发时计算）。
- 自绘标题栏菜单、macOS 原生菜单、全局快捷键共用同一份贡献点数据，不再各自维护一份。
- 后续阶段补充 `toolbar`、`editor/context`（编辑器右键菜单）、`explorer/context`（项目树右键菜单）等菜单位置。

### 6.3 编辑器提供者

```jsonc
"contributes": {
  "editors": [
    {
      "id": "ycide.eyc.table",
      "displayName": "表格代码编辑器",
      "selector": ["*.eyc", "*.egv", "*.ecs", "*.edt", "*.ell", "*.erc", "*.ecc"],
      "priority": "default",          // default | option（可在「打开方式」里选）
      "ui": { "type": "web", "entry": "ui/table-editor.html" }
    }
  ]
}
```

- 同一种文件可以有多个编辑器（表格模式 / 文本模式），用户通过「打开方式」切换。现在的「表格模式异常时回退文本模式」变成宿主的通用能力：编辑器插件崩溃 → 用 `option` 级别的编辑器打开。
- 编辑器 ↔ 宿主的接口：

| 方向 | 消息 | 说明 |
|---|---|---|
| 宿主 → 编辑器 | `editor/open { uri, version, text, viewState }` | 打开文档 |
| 宿主 → 编辑器 | `editor/didChangeDocument { version, edits }` | 外部修改（AI、其他视图） |
| 宿主 → 编辑器 | `editor/decorationsChanged { kind, ranges }` | 断点、调试行、diff 高亮 |
| 宿主 → 编辑器 | `editor/reveal { range }` | 跳转到行 / 子程序 |
| 宿主 → 编辑器 | `editor/executeAction { action }` | 复制、粘贴、查找等 |
| 编辑器 → 宿主 | `documents/applyEdit` | 提交修改 |
| 编辑器 → 宿主 | `editor/selectionChanged { ranges }` | 光标变化（状态栏、属性面板联动） |
| 编辑器 → 宿主 | `editor/saveViewState` | 滚动位置、折叠状态 |

### 6.4 渲染后端（表格 / 流程线）

这是表格编辑器插件**内部的二级扩展点**，由表格编辑器插件定义、由渲染后端插件实现。

```
表格编辑器插件
  ├─ 模型层：调用语言服务 eyc/blocks、eyc/flowLines
  ├─ 布局层：算出行高、列宽、单元格矩形、流程线坐标 → 生成「绘制指令表」
  ├─ 交互层：光标、选区、输入法（隐藏 textarea）、快捷键、拖拽
  └─ 渲染后端（可替换）：只负责把绘制指令表画出来
        ├─ ycide.render.dom      （现有实现，第一个后端）
        └─ ycide.render.canvas   （Canvas 2D / WebGL，绘制放在 Worker 里）
```

**绘制指令表（Display List）**：与具体图形 API 无关的描述。

```ts
type DisplayItem =
  | { op: 'rect';  x: number; y: number; w: number; h: number; fill?: Color; stroke?: Color }
  | { op: 'text';  x: number; y: number; text: string; font: FontId; color: Color; clip?: Rect }
  | { op: 'line';  x1: number; y1: number; x2: number; y2: number; color: Color; width: number; dash?: number[] }
  | { op: 'polyline'; points: number[]; color: Color; width: number; arrow?: 'end' }
  | { op: 'icon';  x: number; y: number; icon: IconId; size: number }

interface DisplayList {
  viewport: { scrollTop: number; scrollLeft: number; width: number; height: number; dpr: number }
  layers: { id: 'background' | 'grid' | 'text' | 'flow' | 'decoration' | 'selection'; items: DisplayItem[] }[]
}
```

**渲染后端接口**：

```ts
interface TableRenderer {
  init(surface: RenderSurface, theme: ThemeTokens): void
  measureText(text: string, font: FontId): { width: number; height: number }  // 布局层依赖
  render(list: DisplayList, dirty?: Rect[]): void                              // 支持局部重绘
  hitTest?(x: number, y: number): HitResult | null                            // 可选，默认由布局层计算
  dispose(): void
}
```

要点：
- 分层（`layers`）让后端可以只重画变化的层，例如移动光标只重画 `selection` 层。
- `measureText` 必须由后端提供，因为不同图形 API 的文字宽度会有差异，布局层要用同一个后端测量的结果。
- 主题颜色通过 `ThemeTokens` 传入，复用现有的 `flowLineTheme.ts` 与主题令牌。
- D2D / GDI 等原生渲染后端不在路线图内：在 Electron 里嵌原生窗口会压住网页浮层（补全框、提示、右键菜单、AI diff 浮层），无法做干净。只有将来换成原生宿主时才考虑，届时清单声明 `"hosts": ["native"]` 和 `"platforms": ["windows"]`（§3.4）。

**Canvas 后端的线程模型（OffscreenCanvas + Worker）**：

```
主线程（UI）                                   渲染 Worker
  ├─ 隐藏 textarea：接收键盘、中文输入法          ├─ 持有 OffscreenCanvas
  ├─ 鼠标事件 → hitTest → 光标/选区               ├─ 接收绘制指令表（或增量）
  ├─ 布局层：生成绘制指令表                       ├─ 按层局部重绘
  └─ 把 <canvas> 通过 transferControlToOffscreen  └─ measureText 结果缓存后回传主线程
     交给 Worker
```

- 绘制在 Worker 里进行，主线程即使在做 React 更新、语言服务回调，也不会卡住滚动和重绘。
- 输入法、焦点、无障碍仍在主线程处理，依靠隐藏 textarea 和光标位置同步实现，保证中文输入正常。
- 文字测量需要在两个线程一致：Worker 用 OffscreenCanvas 测量并按「字体 + 文本」缓存，主线程的布局层使用这份缓存。
- 绘制指令表只传变化的部分（按行或按层的增量），避免每帧整表跨线程拷贝。

> **实现状态（阶段 3、4 落地的范围：流程线层）**
> - 实际落地的渲染面只有流程线（`eycTable.flowLines`）。贡献点是 `renderers`：`{ id, displayName, surfaces, implementation }`，渲染实现直接操作编辑器界面，只有内置插件可以提供（第三方渲染后端要等阶段 5 的权限与隔离）。设置 → 编辑器 →「流程线渲染」选择后端（`tableRendererId`），选的后端不可用时回到 DOM。
> - 「绘制指令表」落地为 `buildFlowLineSlots`（`src/renderer/src/components/Editor/editorFlowRenderUtils.tsx`）：每行算出流程线格与每格要画的元素（同一套 class 语义），DOM 后端直接输出成元素，图像后端按 CSS 里的同样几何画出来，两者画的是同一份结构。
> - 内置两个后端：`ycide.render-dom`（默认，不可停用）与 `ycide.render-image`。图像后端把整行流程线生成一张矢量图（SVG）当背景，每行只占一个元素；同样结构的行只生成一次并缓存。没有用 Canvas 位图：编辑器有 CSS 缩放，行常落在半像素位置，位图贴上去线条发虚；矢量图由浏览器在最终位置光栅化，和 DOM 一样对齐像素。也没有放进 Worker：生成按结构缓存，滚动时只剩取缓存，没有可以挪走的绘制开销。
> - 表格本身（单元格、文字、输入）仍是 DOM，原因见阶段 4 的实现状态：测量表明剩下的开销主要在表格行本身，而整表改成 Canvas 绘制需要重做光标、选区、输入法与全部交互，是单独的大工程。

### 6.5 编译器后端

```jsonc
"contributes": {
  "compilers": [
    {
      "id": "ycide.zig",
      "displayName": "Zig 编译器",
      "targets": ["windows-x64", "windows-x86", "linux-x64", "macos-arm64", "android-arm64"],
      "acceptsImplementations": ["cpp", "objcpp"]   // 能编译哪些语言写的支持库实现，见下文
    }
  ]
}
```

**编译器可卸载、可替换。** 编译器是普通插件，第三方可以提供基于 LLVM 的编译器，或者完全自己写的编译器。为此：

- 编译器协议（下表）是**公开稳定接口**，内置的 Zig 编译器不能使用任何私有接口，否则第三方无法实现同等能力。
- 可以同时安装多个编译器。项目文件（`.epp`）里记录选用的编译器 ID，没有记录时使用设置里的默认编译器。
- 没有安装任何编译器时，IDE 仍然可以编辑代码，编译、运行按钮置灰并提示「未安装编译器」。
- 编译器拿到的输入是**语言服务给出的语法树 + 已加载支持库的元数据**，而不是自己再解析一遍源码，保证不同编译器对同一份代码的理解一致。（语法树格式另行定义，基于现有 `transpiler/` 的 AST。）
- **支持库实现与编译器的匹配**：支持库在清单里声明实现语言（现有的 `implementations.<平台>.language`，如 `cpp`），编译器声明 `acceptsImplementations`。用到某个支持库、但编译器不接受它的实现语言时，编译前报错并指出是哪个库。这样第三方编译器即使不处理 C++，也可以只配合用自己语言写实现的支持库。

| 方法 | 说明 |
|---|---|
| `compiler/prepare` | 预热（现 `compilerWarmup.ts`），返回就绪状态 |
| `compiler/build { project, target, mode, debug, breakpoints, previewWindow, unsavedFiles }` | 编译，进度与输出走 `$/progress` |
| `compiler/run` / `compiler/stop` / `compiler/isRunning` | 运行控制 |
| `compiler/diagnostics`（通知） | 编译诊断，已经映射回易语言源码位置（现 `reportFriendlyCppDiagnostic`） |

- 现有 `CompilerHost` 接口（`emitOutput` / `notifyProcessExit` / `readCompilerSettings` …）几乎可以直接对应到协议消息，这是改造成本最低的一块。
- 编译器通过 `libraries/*` 接口向宿主查询已加载支持库，不再直接 `import libraryManager`。

### 6.6 支持库

支持库是**数据插件**，沿用现有格式，只是在外面包一层 `plugin.json`：

```jsonc
{
  "id": "ycide.webview2",
  "displayName": "WebView2 浏览器支持库",
  "version": "1.0.0",
  "runtime": { "type": "none" },
  "targets": ["windows"],                // 目标平台，见 §3.4；宿主平台不限
  "contributes": {
    "libraries": [
      {
        "guid": "7A2E94C1B6D34F08A5E1C9F2D7B30461",
        "info": "data/webview2.library.json",
        "commands": "data/webview2.commands.ycmd.json",
        "windowUnits": "data/webview2.window-units.json",
        "implementations": { "windows": "data/impl/windows.cpp" }
      }
    ]
  }
}
```

- 现有的远程索引、zip 包、sha256 校验、安装/卸载（`libraryManager` + `shared/library-store.ts`）直接作为插件商店的基础。
- **需要补齐的缺口**：编译器里写死的核心库控件代码生成（14 个 `buildStd*Codegen`、控件方法 `translateListLikeMethodCall` 等）要搬到 krnln 自己的 `window-units.json` 模板里。模板表达不了的复杂控件，允许支持库提供一个**代码生成脚本**（`codegen` 字段，运行在编译器进程内的受限沙箱里），而不是继续写在编译器里。
- **核心支持库 `ycide.krnln` 也是普通的可卸载命令库。** 卸载后 IDE 变成「空壳」：可以编辑代码，但没有核心命令、没有基础窗口组件。为此要做三处改动：
  1. 去掉启动时「核心库缺失或被修改就报错退出」的逻辑（现 `libraryManager` 的完整性校验），改为：缺失时提示并以空壳模式运行；文件被篡改时只停用该库并提示。
  2. 编译器、语言服务、窗口设计器里所有写死的 krnln 知识（控件代码生成、控件方法翻译、控件类型名）全部搬进 `ycide.krnln` 自己的数据文件，由 krnln 作为普通支持库提供。
  3. 按 §6.11 划清「语言本身」与 krnln 的边界：流程控制和基本数据类型归语言，krnln 只提供普通命令、常量和窗口组件。

### 6.7 AI

拆成三类贡献点：

| 贡献点 | 谁提供 | 说明 |
|---|---|---|
| `aiProviders` | 模型插件（DeepSeek、GLM、OpenAI 兼容……） | 实现 `ai/chat`、`ai/chatStream`、`ai/chatWithTools`。替代 `ai-assistant.ts` 的 `resolveProvider` 硬编码 |
| `aiTools` | **任何插件** | 给 AI 提供工具。现在写死在 `App.tsx` 的 7 个工具（`list_files`、`read_file`、`open_file`、`edit_file`、`terminal_send`、`terminal_read`、`terminal_last_command`）分别由工作区、文档、终端插件贡献；编译器插件可以再贡献 `compile_project`，调试器插件贡献 `get_variables` |
| `aiAgents` | Agent 插件 | Agent 循环（问答 / 编辑 / Agent / Plan 模式），调用宿主聚合后的工具列表 |

工具声明：

```jsonc
"aiTools": [
  {
    "name": "compile_project",
    "description": "编译当前项目并返回错误列表",
    "parameters": { "type": "object", "properties": { "target": { "type": "string" } } },
    "risk": "exec"          // read | write | exec，决定是否需要用户确认
  }
]
```

- `risk: write | exec` 的工具调用前由宿主统一弹确认（可在设置里对单个工具设为「总是允许」）。
- AI 对代码的修改统一走 `documents/applyEdit`，diff 高亮走 `decorations`，因此任何编辑器都能显示 AI 改动，不再只有表格编辑器支持。

直接采用 **DAP（Debug Adapter Protocol）**：

- 断点、单步、变量、调用栈都是 DAP 标准消息，宿主负责调试 UI（断点栏、变量面板、调用栈）。

### 6.11 语言本身与核心支持库的边界

结论（§13.1 第 8 条）：**流程控制和基本数据类型归语言本身**，由语言服务 `ycide.lang.eyc` 定义，所有编译器插件必须实现；卸载 `ycide.krnln` 后它们照样可用，流程线也照常显示。

| 归属 | 内容 | 由谁提供 |
|---|---|---|
| **语言本身** | 流程控制：如果 / 如果真 / 判断开始 / 判断 / 否则 / 默认，判断循环首、循环判断首、计次循环首、变量循环首及对应的结束标记，到循环尾、跳出循环、返回、结束 | 语言服务（语法、块结构、流程线）+ 每个编译器（代码生成） |
| **语言本身** | 基本数据类型：字节型、短整数型、整数型、长整数型、小数型、双精度小数型、逻辑型、日期时间型、文本型、字节集、子程序指针，以及数组 | 同上 |
| **语言本身** | 声明结构：程序集、子程序、参数、局部/程序集/全局变量、常量、自定义数据类型、DLL 命令、类模块 | 同上 |
| **语言本身** | 运算符与字面量：算术、比较、逻辑运算，文本、数值、逻辑、日期时间字面量 | 同上 |
| **核心支持库 krnln** | 普通命令（信息框、取文本长度、到文本……）、常量（#换行符等）、窗口组件（窗口、按钮、编辑框……）及其属性、事件、方法 | `ycide.krnln` 的数据文件与平台实现 |

对现有代码的影响：
- `eycFlow.ts` 中的流程关键字表（`FLOW_START`、`FLOW_LOOP_KW`、`FLOW_KW` 等）和 `eycBlocks.ts` 的块解析迁入 `ycide.lang.eyc`，作为语言定义的一部分，不再出现在任何支持库清单里。
- 编译器里流程控制和基本类型的代码生成保留在编译器插件内（这是编译器必须实现的语言能力）；而控件、普通命令相关的硬编码按 §6.6 搬进 krnln。
- 语言的这部分定义写成独立规范文档（《易承语言核心语法规范》），作为第三方编译器的实现依据。
- 补全、命令说明里，流程控制关键字的说明文本也归语言服务提供，不依赖 krnln 的帮助文件。

## 7. UI 插件的运行方式

| 宿主 | `ui.type: "web"` | `ui.type: "native"` |
|---|---|---|
| Electron 宿主（当前） | 运行在独立 iframe 中（`sandbox` + 独立 CSP），通过 `postMessage` 走协议 | 不支持 |
| 原生宿主（将来） | 在对应区域嵌入 WebView2 | 加载插件 DLL，提供 HWND 或 D2D 设备上下文 |

- **内置插件的特例（性能）**：iframe 之间传大量消息有开销。官方内置的编辑器插件在 Electron 宿主里允许以**同进程模块**的方式加载（直接 import，共享 React 运行时），但仍然只能使用协议定义的接口（编译期通过类型检查和 lint 规则保证不越界）。这样既不牺牲当前性能，又保证将来能迁到原生宿主。
- 主题令牌通过 CSS 变量注入到 web UI 插件；原生插件通过 `theme/get` 获取颜色值。

## 8. 权限与安全

### 8.1 权限声明

| 权限 | 含义 |
|---|---|
| `workspace:read` / `workspace:write` | 读写当前项目目录 |
| `fs:any` | 读写任意路径（需用户显式同意，内置插件除外） |
| `net:<域名>` | 访问指定域名；`net:*` 需要显式同意 |
| `process:spawn` | 启动子进程 |
| `terminal` | 访问内置终端 |
| `secrets:own` | 读写本插件自己的密钥 |
| `ai:invoke` | 调用 AI 模型（会消耗用户额度） |
| `documents:write` | 修改打开的文档 |
| `workbench:commands` | 执行 IDE 内置命令（菜单里的功能，如保存、编译、运行）；插件之间互相调用命令不需要（阶段 5 实现时补充） |

### 8.2 执行措施
- 宿主对每个协议请求检查调用方插件的权限，越权返回 `-33001`。
- 第三方 JS 插件运行在独立进程，开启 Node 的权限模型（`--permission`，具体可用性需在 Electron 自带的 Node 版本上验证）限制文件和子进程访问，作为第二道防线。
- 继续使用现有 `security/pathGuard.ts` 做路径校验。
- 插件包沿用支持库商店的 sha256 校验；第三方插件后续增加发布者签名。
- 安装第三方插件时展示权限列表，用户确认后才安装。

## 11. 迁移路线

- 把 `buildStd*Codegen` 等核心库控件代码生成迁到 `ycide.krnln` 的模板 / codegen 脚本。
- 核心支持库改为可卸载：去掉启动强校验，支持空壳模式（§6.6）。

> **实现状态（已完成，含下列遗留项）**
> - 编译器插件化：新增 `compilers` 贡献点与主进程编译器服务 `src/main/compilers/compilerService.ts`。内置 Zig 编译器由数据插件 `ycide.compiler-zig` 声明（实现仍在主进程与编译工作线程里）；第三方编译器用 `commands.build / run / stop / isRunning / continueDebug` 命令实现，经插件 API `ycide.output.appendLine` 写编译输出。选择顺序：项目文件 `Compiler=` → 设置「默认编译器」（新设置项 `compilerId`）→ 内置 Zig → 第一个可用。编译前检查编译器的 `acceptsImplementations` 能否处理已加载支持库的实现语言。停用全部编译器后编译、调试菜单置灰（上下文键 `compilerAvailable`），预热状态显示「没有可用的编译器」。
> - 支持库插件化：`lib/` 下每个支持库目录带 `plugin.json`（`libraries` 贡献点，数据插件）；插件服务同时扫描内置支持库目录与用户安装的支持库目录。支持库插件被停用（或因依赖不可用）时，支持库管理视同未安装，并随每次编译请求同步给编译工作线程。商店索引条目新增 `kind`（library / plugin / theme，缺省 library），支持库窗口只列 library；插件、主题的商店安装界面在阶段 5 做。
> - 核心库知识外移：编译器里按组件名判断的代码（83 处）与默认 Win32 类名、样式表全部移到各支持库的 `control-traits.json`（核心库、webview2、script），编译器只按英文「特征」查询（`isControl(类型, 'button')` 等）。用包含 58 种组件名的测试项目在编译、运行、预览主窗口、预览子窗口四种模式下对比，生成的 C++ 与改造前逐字节一致；改动特征数据后对比能发现差异。
> - 核心支持库可卸载：启动时核心库校验失败不再退出，改为停用核心库、以空壳模式运行并提示；插件管理里也可以直接停用 `ycide.krnln`。
> - 安全：插件清单里的 `builtin` 只有随安装包发布的目录（内置插件、`lib/`）才认可；用户安装的插件写 `builtin: true` 也按非内置处理，拿不到内置模型提供方的 API Key 字段，提供的 AI 工具调用前仍需确认（阶段 1 遗留的漏洞）。

### 阶段 4：Canvas 渲染后端（约 4–6 周）
- 开工前先定性能目标（例如：一万行文件中按键到显示的延迟、滚动帧率、打开时间的具体数值），并录制现有 DOM 版本作为基线。

> **实现状态（流程线层已完成；整表 Canvas 未做）**
> - 性能录制：`tests/perf/table-editor-perf.spec.js`（`npx playwright test --config tests/perf/playwright.perf.config.js`），生成约一万行、多层嵌套流程的文件，在真实 IDE 里测打开、逐帧滚动到底、逐字输入，并做 CPU 剖析。环境变量 `YCIDE_TABLE_RENDERER` 选后端，`YCIDE_PERF_CPU_THROTTLE` 模拟慢机器，`YCIDE_PERF_INJECT_CSS` 用于诊断（例如隐藏流程线看它占多少）。
> - 性能目标（10163 行）与实测：
>
> | 指标 | 目标 | 改造前 DOM | DOM（阶段 3 修正后） | 图像后端 |
> |---|---|---|---|---|
> | 正常 CPU：打开 | ≤ 500ms | 379ms | 345ms | 338ms |
> | 正常 CPU：滚动每帧中位数 / 长任务 | 跟满刷新率、无长任务 | 17.4ms / 0 | 17.4ms / 0 | 17.4ms / 0 |
> | 正常 CPU：输入延迟中位数 / P95 | ≤ 50ms / ≤ 100ms | 28.5 / 65ms | 40 / 67ms | 36 / 60ms |
> | 4 倍降速：滚动每帧中位数 | ≤ 33ms（30 帧） | 52.8ms | 50.1ms | 44.9ms |
> | 4 倍降速：滚动长任务（1456 帧中） | — | 283 | 274 | 67 |
> | 4 倍降速：输入延迟中位数 / P95 | ≤ 100ms / ≤ 200ms | 256 / 357ms | 104 / 266ms | 103 / 254ms |
>
> （正常 CPU 下输入延迟两次运行之间波动约 ±10ms。）
> - 结论：正常机器上 DOM 已达标。慢机器上图像后端让滚动快约 10%、长任务减少约四分之三，但仍未达到 30 帧；把流程线整个隐藏掉，4 倍降速滚动也只到 42.9ms，说明剩下的开销在表格行本身（单元格、文字的样式计算与布局），不在流程线。输入延迟的大头已由阶段 3 的 `extractFlowKw` 缓存解决（256 → 103ms），换后端影响不大。

> - 签名与商店（§8.2、§13.1 第 4 条）：商店索引条目新增 `publisher`、`signature`、`permissions`，索引带 `publishers` 公钥表。安装时校验 sha256、Ed25519 发布者签名（公钥首次见到后固定在本机，之后变化即拒绝）、包内清单的 ID 与发布者、主题包不带代码、申请的权限不超出用户确认的范围；未签名的包需要用户明确同意。打包签名工具 `scripts/plugin-pack.mjs`。
> - 界面：「工具 → 插件管理」——已安装插件（状态、未启用原因、运行在哪种进程、权限，启用 / 停用 / 授权 / 收回授权 / 卸载）与商店（插件、主题，安装前逐条列出权限，敏感权限标红）。
> - 开发：开发目录文件变化后自动重新加载插件（`YCIDE_PLUGIN_HOT_RELOAD=0` 关闭）；新增密钥 API `ycide.secrets`（系统安全存储加密、按插件隔离）与插件存储目录 `context.storagePath`。开发文档 `docs/插件开发指南.md`，模板 `templates/plugins/js-hello`、`templates/plugins/eyc-hello`。
> - 遗留：①`ai:invoke`、`terminal`、`workspace:write` 只定义了权限，还没有对应的插件 API；②第三方网页编辑器仍不能联网（CSP 未按 `net:` 权限放开）；③商店索引本身靠 HTTPS 保证完整性，没有官方对索引签名；④`net:` 拦截只覆盖 TCP / TLS，UDP（dgram）未拦截；⑤可执行文件插件在系统层面不受限制（安装时已向用户说明）。

### 阶段 6（按条件再评估）：原生宿主
- 默认不做。只有满足 §13.1 第 2 条的触发条件时，才启动约 2 周的技术验证（候选方向：Qt 6 + C++，原生 UI 插件用 C ABI，不暴露 Qt 类型）。
- 验证通过后再决定是否实现原生宿主与 D2D 渲染后端。

> 时间估算按 1–2 名主力开发、同时维持日常修复来估，仅供排期参考。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 迁移期间新旧代码并存，复杂度上升 | 每个阶段有明确完成标准；旧代码路径在阶段结束时删除，不长期保留双轨 |
| iframe / IPC 带来性能损耗 | 内置编辑器同进程加载（§7）；大数据走文件路径；渲染后端在编辑器进程内，不跨进程 |
| 协议设计反复修改 | 先用内置插件验证一个大版本再开放；`proposed` 接口机制 |
| 编译产物在迁移中被改坏 | 阶段 2 用测试项目做编译产物逐字节对比的回归测试 |
| 与正在开发的功能冲突（调试器、AI Agent/Plan 模式） | 调试器直接按 DAP 插件形式开发；AI 新模式在阶段 1 之后基于新接口开发 |

## 13. 决策记录与待决问题

### 13.1 已拍板

| # | 问题 | 结论 |
|---|---|---|
| 1 | 第三方插件的开发语言 | JS/TS 为主力；协议层同时支持任意语言的可执行文件插件（stdio + JSON-RPC）。阶段 5 推出「插件开发支持库」，让用户用易语言写插件。插件必须声明平台标签，当前平台不支持的插件禁止加载（§3.4） |
| 2 | 宿主框架 | **继续使用 Electron**，原生宿主暂不做。插件协议保持与框架无关以保留后路。出现以下任一情况时重新评估（候选：Qt 6 + C++）：① 阶段 4 实测 Canvas 后端仍达不到性能目标；② 内存占用或启动速度成为用户的主要抱怨；③ 出现必须用 D2D/GDI 绘制的明确需求。D2D 渲染后端移出路线图 |
| 3 | 内置插件同进程加载 | 接受双轨：官方内置插件同进程加载，但只能使用协议定义的接口（类型检查 + lint 约束）；第三方插件隔离运行 |
| 4 | 插件商店 | 与支持库商店合并为同一个索引，条目用 `kind` 区分（`library` / `plugin` / `theme`）。商店尚未上线，不需要兼容旧索引 |
| 5 | 哪些插件不可卸载 | 见下表。编译器和核心支持库都可以卸载 |
| 6 | 会员额度与第三方 AI 插件 | 会员额度只管官方托管的模型服务；用户自带 API Key 的模型不受限制；官方额度接口只对官方模型插件开放 |
| 7 | 插件 ID 规范 | `发布者.名称`，只用小写英文、数字、短横线；`ycide` 发布者保留给官方；中文显示名允许重复（商店同时显示发布者）；支持库额外保留 GUID 作为第二唯一键，兼容旧项目 |
| 8 | 语言本身与核心支持库的边界 | 方案 A：流程控制、基本数据类型、声明结构、运算符归语言本身，卸载 krnln 后仍可用；krnln 只提供普通命令、常量和窗口组件（§6.11） |

卸载规则：

| 档位 | 插件 | 说明 |
|---|---|---|
| 不可卸载、不可停用 | 项目管理（`ycide.project`）、语言服务（`ycide.lang.eyc`）、文本编辑器（`ycide.editor.text`） | 文本编辑器是所有编辑器崩溃时的兜底 |
| 不可卸载，但可被替换 | 表格编辑器、DOM 渲染后端 | 可以把默认值切到第三方插件，内置的始终保留作为回退 |
| 可停用、可卸载 | 其余全部，**包括编译器和核心支持库 `ycide.krnln`** | 没有编译器：能编辑、不能编译。没有 krnln：变成空壳，没有核心命令和基础窗口组件 |
