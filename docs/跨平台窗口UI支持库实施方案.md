# 跨平台窗口 UI 支持库实施方案

> 日期：2026-11-13
> 状态：实施基线与修订方案；窗口提供者及 EUI Windows x64 实验链路已接通。2026-11-14 按窗口、控件与平台实现分层修订；新能力按本次修订实施，Linux/macOS 与正式分发尚未完成。
> 范围：桌面窗口项目的窗口提供者选择、设计器适配、编译运行和分发。
> 用途：后续开发按本文的阶段与验收门槛推进，不将讨论中的设想当作已有能力。

## 1. 目标与已确定的方向

1. 利用现有插件与支持库机制，让窗口 UI 实现成为项目可选择的能力，而不是由宿主系统隐式决定。
2. 新建窗口程序时，根据**目标平台**筛选能够提供顶层窗口的支持库；多个候选让用户选择，一个候选自动选中并显示结果，没有候选明确阻止创建。
3. 保留现有 Win32 路线，新增独立的跨平台自绘窗口支持库，不为接入新引擎推翻已有项目和核心库。
4. EUI-NEO 作为第一个自绘引擎候选，先做最小验证，再决定正式接入；不直接替换 IDE 的 Electron/React 外壳。
5. 项目保存稳定的窗口提供者身份；设计器、工具箱、编译器和预览均使用同一份解析结果。
6. EUI 自绘窗口统一窗口外壳及 EUI 自绘控件的外观、布局与交互；系统窗口仅作为无装饰承载。控件可来自不同支持库：目标平台适用的原生控件保留平台原生外观，不要求与 EUI 自绘控件像素一致。Win32 窗口保留原生外壳；系统文件对话框等独立交互仍允许平台差异。

最终期望的选择结果：

| 目标平台 | 已验证且启用的提供者 | 新建行为 |
|---|---|---|
| Windows | Win32、EUI 自绘 | 要求选择，不静默决定 |
| Linux | EUI 自绘 | 自动选中并说明 |
| macOS | EUI 自绘 | 自动选中并说明 |

**该表是目标状态，不是当前能力清单。** EUI 尚未验证的平台不能提前声明可用；此时该平台可能没有候选，必须展示原因。

## 3. 非目标与防偏约束

- 本次不重写 IDE，不更换 React/Electron，不把应用窗口库用作 IDE 渲染器。
- 不在第一阶段拆分、重命名或删除 `krnln`；先将其中现有 Win32 窗口能力注册为提供者。
- 不承诺已有 Win32 项目一键转换为 EUI 项目；已有窗体的控件身份和数据在目标平台变化时必须保留，逐项诊断不支持项，不自动替换或删除。
- EUI 自绘控件与平台原生控件是不同控件类别：不把原生控件伪装成 EUI 自绘控件，也不要求原生控件呈现跨平台相同外观。
- 不将 Android、iOS、HarmonyOS 纳入本期；现有移动项目流程保持原行为。
- 不为接入 EUI 新建另一套命令、属性、事件和项目管理体系；优先复用既有元数据协议。
- 不把 GLFW、SDL2、OpenGL、Vulkan 作为普通用户新建项目的必选项；首版只支持经过验证的固定组合。
- 不宣称跨平台一定能够跨系统编译。目标平台支持、工具链可构建、宿主可本地运行是三种不同能力。
- 不用“加几个平台判断”代替后端接口，也不提前抽象没有第二个实现需求的通用框架。

## 4. 概念和职责

### 4.1 三个身份必须分开

- **支持库/插件**：安装、启用、依赖、版本和分发的单位。
- **窗口 UI 提供者**：声明如何创建顶层窗口、管理生命周期及编译运行；一个支持库可提供零个或多个。提供者另外声明可承载的控件适配器，不枚举或拥有控件类型。
- **控件类型**：带稳定身份的窗口单元，声明其控件适配器及已实现的目标平台；控件来源、目标平台实现和窗口外壳是不同维度。

有可视控件不等于能提供顶层窗口。图片组件、WebView 等不能仅因具有 UI 就出现在新建项目的窗口提供者列表里。

### 4.2 职责分配

| 层 | 职责 |
|---|---|
| 宿主 | 管理项目状态、窗口提供者注册、目标平台筛选、控件兼容诊断、设计器交互和协议边界 |
| 窗口支持库 | 提供顶层窗口单元、窗口生命周期/编译适配，并声明可承载的控件适配器 |
| 控件支持库 | 提供稳定控件身份、属性/事件、控件适配器、目标平台实现及设计期描述；不依赖窗口库归属 |
| 编译器 | 将公共语言/项目数据交给选定后端，完成源码、入口、资源、链接与调试产物生成 |
| 控件适配器 | 将控件库身份、属性、事件和生命周期映射到 EUI 自绘控件或目标平台原生控件 |
| EUI-NEO | 承担自身窗口、输入、布局与绘制，不直接管理 ycIDE 项目文件 |

IDE 的“渲染后端插件”和用户程序的“窗口 UI 提供者”是不同贡献点，不能混用标识和注册表。

## 5. 元数据与协议设计

### 5.1 提供者贡献点

拟在插件清单中增加 `contributes.windowUiProviders`。以下是**拟议契约示例，不是现有可用配置**：

```json
{
  "windowUiProviders": [
    {
      "id": "ycide.krnln.win32",
      "displayName": "Win32 原生窗口",
      "library": "krnln",
      "apiVersion": 1,
      "targets": ["windows-x64"],
      "rootWindowType": "krnln.window",
      "runtimeAdapter": "win32",
      "designerAdapter": "win32"
    }
  ]
}
```

上例架构标签仅演示写法，正式清单必须列出实际验证过的目标，不据此缩减现有 Win32 支持范围。

约束：

1. `id` 在注册表内唯一、稳定、由所属插件命名空间约束；重复声明是诊断错误，不采取“先到先得”。
2. `targets` 描述窗口能力，并与插件目标、控件目标、编译器能力取交集；未声明不得推断成支持所有平台。
3. 平台和架构使用既有项目规范化工具，兼容已有平台值，不另造不兼容枚举。
4. `rootWindowType` 必须解析到所属支持库实际存在的顶层窗口单元。
5. adapter 标识必须解析到已注册、版本兼容的实现；不是任意文件执行入口。
6. 区分“已声明”“依赖缺失”“工具链不满足”“可构建”“可本地运行”等状态，向导不能把它们合并为一个布尔值。
7. 编译器必须声明或协商支持的 provider/adapter API。仅 `acceptsImplementations: ["cpp"]` 不足以证明可构建 EUI。
8. v1 先支持官方内置适配器；未来第三方执行适配沿用插件服务进程、命令、权限和错误通道，不新增主进程任意脚本入口。

### 5.2 控件身份、适配器与平台能力

新格式控件至少具有稳定的 `libraryId`、`typeId`，显示名不参与唯一性判定。窗口提供者由项目解析上下文确定。控件元数据使用独立的 `controlAdapters` 和 `supportedTargets` 描述运行能力；窗口提供者使用 `controlAdapters` 声明可宿主的适配器。两个同名字段处于不同对象且职责不同：前者是控件实现，后者是窗口宿主能力。

顶层窗口单元也必须在支持库元数据中显式声明 `topLevel: true` 和所属 `uiProviders`；`krnln` 的 `Window` 属于 Win32 提供者，EUI 顶层窗口仍由 `eui` 库单独提供。仅在插件清单注册提供者而未标记窗口单元，向导会因缺少顶层窗口而禁用该选项。

- **窗口提供者不是控件来源白名单。** 一个窗口可以使用多个支持库中的控件；控件不需要与窗口提供者属于同一支持库，也不需要自己提供顶层窗口。
- 控件元数据声明自身已实现的适配器和目标；提供者声明可宿主的适配器。控件可用性是这两者与目标平台的交集，而不是控件库必须逐个列出窗口提供者 ID。
- EUI 自绘控件使用 EUI 适配器，负责跨其已验证平台保持一致的主题与交互；平台原生控件使用目标平台的原生适配器，例如 Windows 的 Win32 控件。EUI 窗口可宿主它所支持平台上的原生子控件；这类控件继续保持原生视觉，不称作 EUI 控件。
- 新建项目工具箱只列出当前目标平台已实现且当前窗口提供者可宿主的控件。没有明确目标能力声明的控件不可被推断为全平台支持。
- 已放置控件的身份由 `.efw` 稳定保存。目标平台变化后，既有控件不按新目标过滤掉：不支持项保留在窗体上并标记/诊断；构建必须报告不可用项，要求用户移除或替换。
- 非可视组件不能一律视为跨后端兼容，也必须声明能力。
- 外部控件只有显式声明适配器、目标能力并通过验证后才能出现在工具箱中。
- 旧 `.efw` 保留名称解析兼容；新格式保存稳定身份。复制粘贴时检查目标适配器和平台，不兼容则拒绝并说明。
- v1 一个项目只选择一个提供者；项目内新增窗口继承该选择，单窗体不允许覆盖成其他后端。

EUI 适配使用 `runtimeType` 选择已实现的 EUI 基础控件。`runtimeType` 是适配器内部类型，不能替代控件本身的稳定 `typeId`；`previewType` 也不能单独当成运行能力证明。实际控件仍由 `libraryId + typeId` 唯一定位，属性/事件定义及编译读写协议从它自身的库读取，使用到的库实现参与链接，图片按运行类型部署。控件单元上的 `uiProviders` 仅用于兼容读取旧元数据；新控件不以该字段绑定窗口提供者。

基础适配仅初始化其标准属性；扩展设计期属性、额外事件或带参/有返回值事件必须另有实际适配，未实现时明确报错，不能丢弃配置继续构建。当前不自动把依赖 Win32 句柄的控件变成 EUI 控件，也不声称已经开放任意第三方自定义绘制 ABI。

#### 当前随仓库提供的控件适配情况

“支持库已加载”只表示命令/元数据已加载，不代表其控件已适配所有窗口提供者或目标平台。临时测试库只用于回归跨库协议，不能作为现有产品控件已接入的验收依据。

| 支持库 | EUI 工具箱中的实际可用组件 | 当前边界 |
|---|---|---|
| `eui` | 按钮、编辑框、标签、图片框 | EUI-NEO 自绘控件；当前 Windows x64 实验实现 |
| `script` | 脚本组件（第三方组件 → 功能组件） | Windows IActiveScript 非可视组件；EUI 路径通过 `EuiScript` 运行适配；不是跨平台脚本引擎 |
| `krnln` | 目标平台适配后显示 | 核心原生控件属于平台 API 控件，不再映射成 EUI 自绘控件；每种控件按其实际适配器/目标声明可用 |
| `webview2` | 浏览框、网页按钮、网页编辑框 | 浏览框是真实 WebView2 子窗口；网页按钮/编辑框为 EUI 适配控件，不执行 HTML 模板。需安装 WebView2 Runtime，地址限 `http(s)://` 或 `about:blank` |
| `spec`、`ycplugin` | 不贡献窗口控件 | 命令库，不应期待每个已加载库都生成一个工具箱分类 |

Win32 原生控件必须以真实平台控件实现承载，不得用 EUI 主题控件替代后仍标记为 Win32。其属性/事件只开放适配器实际支持的部分，未实现属性必须在设计期或构建时报错。EUI 自绘控件使用 EUI 主题与交互。`webview2` 浏览框以原生子窗口承载既有实现；网页按钮/编辑框复用 EUI-NEO 控件和项目主题，不保持原 HTML 模板外观。

`EuiScript` 使用现有脚本库 ABI，支持语言、超时及只读错误信息，以及执行、计算表达式、运行、清除方法；设计期语言只允许 JScript/VBScript，超时为有符号 32 位毫秒值。组件在窗口创建事件前初始化，在窗口关闭时销毁并移除引擎状态；关闭重开重新应用设计值，实例互相隔离。设计器只显示非可视组件占位，运行时不绘制、不创建子 HWND，因此不改变整窗自绘方案。

现有库的实际验收需覆盖 `script`、核心 `krnln` 控件及 `webview2` 控件：工具箱/属性/事件、真实编译链接、控件属性读写、窗口创建和关闭。本轮自动化已增加核心控件与 WebView2 控件共同参与的 EUI 项目原生编译运行测试，以及其身份、属性、事件和输入范围校验；跨主题与桌面读屏仍需独立验收。原有临时同名库测试继续保留，但不替代上述产品用例。

### 5.3 项目持久化

沿用 `.epp` 键值格式，拟增加：

```ini
UiProvider=ycide.krnln.win32
UiProviderApiVersion=1
UiProviderPluginVersion=1.0.0
```

这些键同样是待实施协议。插件版本记录项目选择时的实际版本，用于复现和升级诊断，不冒充已经存在的自动依赖锁定系统。

- 保留现有 `OutputType=WindowsApp` 的兼容含义，不因名字包含 Windows 就将其他平台 UI 项目改成新类型。
- 提供者身份是权威选择；`.efw` 的新格式版本、控件类型字段随协议一起制定和校验，不重复保存可互相矛盾的后端选择。
- 主进程创建、普通打开、编译器独立读取、预览、另存为、项目属性保存及前后端 IPC 必须保持一致。
- 打开时重算依赖状态，但不能重新选择提供者。记录版本与安装版本不同要显示差异；API 主版本不兼容时阻止构建。
- v1 不自动下载或静默升级依赖；缺少指定版本时提供明确的恢复/升级说明，用户确认后才能更新记录。
- 含新字段或新控件格式的项目不得被旧版 IDE 无损支持的承诺误导；确定必要的项目格式版本门槛，旧客户端可能丢弃字段的风险必须在发布说明中写清。

## 6. 新建项目与后续操作

### 6.1 新建流程

1. 用户选择桌面目标平台和“窗口程序”。
2. 宿主从已启用支持库收集窗口提供者，校验身份、窗口单元、目标及适配器。
3. 根据目标与当前编译器/工具链生成可用项及不可用原因；架构尚未选择时注明待验证架构，创建前完成校验。
4. 在现有对话框内展示“窗口 UI 支持库”选择区，不再叠加第二个模态对话框。
5. 零个可用项：阻止创建，展示缺少支持库、适配器或工具链等原因。
6. 一个可用项：自动选中，仍展示名称、支持目标及当前状态。
7. 多个可用项：要求用户明确选择，不按插件扫描顺序默选。
8. 平台切换后重新筛选；原选择不兼容则清除并通知，兼容则保留。
9. 确认时主进程再次验证，验证通过后才写入项目和启动窗体，避免在渲染进程检查后出现插件被停用的竞态。

控制台、动态库和现有移动项目不展示这个桌面窗口选择区。

### 6.2 打开、修改平台、缺失依赖

- 提供者缺失或停用：允许查看和编辑源文件；窗体显示带诊断的占位预览，禁止运行，不替换后端、不删除未知属性。
- 依赖不兼容：展示提供者、期望版本/API、实际版本和修复路径。
- 修改平台：允许保存目标平台变化，不自动更换窗口提供者或改写控件。设计器保留全部已放置控件，并将目标平台未实现的控件标为不支持；新控件工具箱按新目标隐藏这些类型。构建检查窗口提供者、控件适配器和工具链，发现不兼容时报告具体类型/位置并阻止产物生成。
- 标记为不支持的控件仍可选中、移动、查看和编辑，以便移除或替换；状态不能只用颜色表达，需有文字/图标提示、属性区说明及可访问名称。平台切回受支持目标后，若实现仍可用则自动恢复正常状态。
- 更换提供者：v1 不提供直接转换入口；未来另立迁移方案，先分析属性/事件映射及数据损失，再预览差异、备份和确认。

## 7. 旧项目兼容规则

1. 缺少 `UiProvider` 的既有桌面窗口项目，按“旧版 Win32 窗口语义”解析，而不是按当前操作系统推断。
2. 首次打开不自动重写项目；通过显式保存/升级操作持久化新字段，并保留原控件含义。
3. 旧项目目标为非 Windows，不因此自动变成 EUI。显示历史后端与目标不兼容的诊断，仍允许编辑。
4. 非窗口项目不要求新增提供者字段。
5. 读取旧控件名称时检测歧义；不能因为安装了同名 EUI 按钮就改变旧按钮类型。
6. Win32 属性默认值、事件签名、生成结果、VC6 现代样式设置和已有调试行为必须保留回归验证。
7. 不能因为用户选择 EUI 就停用整个 `krnln`；它的核心命令仍可能是公共运行时依赖。

## 8. EUI-NEO 候选验证与适配

### 8.1 文档依据与当前结论

已查阅上游文档（2026-11-13，`main` 分支内容，非固定版本）：

- [中文介绍](https://github.com/sudoevolve/EUI-NEO/blob/main/README.zh-CN.md)
- [集成指南](https://github.com/sudoevolve/EUI-NEO/blob/main/docs/guides/integration.md)
- [布局系统](https://github.com/sudoevolve/EUI-NEO/blob/main/docs/guides/layout.md)
- [平台能力](https://github.com/sudoevolve/EUI-NEO/blob/main/docs/guides/platform.md)

文档说明其采用 C++17，支持 GLFW/SDL2 与 OpenGL/Vulkan；提供 SDK/CMake 接入，支持逻辑坐标和 Stack 显式定位。它具备候选价值，但文档不等于实际兼容性证明。

已知需核验的约束：

- 集成入口会加入程序入口、输入和渲染循环；不能与现有启动代码重复定义入口。
- Linux 文件对话框依赖 `zenity/kdialog`，macOS 文档使用 `osascript`；分发时必须说明依赖与错误行为。
- 上游文档列出窗口交互移动/缩放在部分平台的限制，尤其需要区分 X11、Wayland 和所选窗口后端。
- 原创代码声明 Apache-2.0；第三方源码、字体、图标、SDK 的分发许可需要分别核对。
- 无障碍、多窗口、中文输入和低资源环境尚未在本项目验证，不提前标为支持。

开始验证前固定具体 commit 或发布版本，记录依赖、补丁、工具链和构建参数，禁止正式构建跟随浮动 `main`。

### 8.2 最小样例

样例必须包含：

- 主窗口、按钮、单行/多行编辑框、标签、图片。
- 中文标题、中文输入、组合输入、光标/选区、复制粘贴。
- 按钮事件触发用户子程序；子程序读写控件属性并立即更新界面。
- 第二个顶层窗口、模态窗口、关闭取消和完整退出。
- Tab/Shift+Tab、可见焦点、默认/取消动作及屏幕阅读器识别。
- 浅色/深色主题、缩放、窗口调整大小。
- 从非项目工作目录启动，仍能找到字体、图片及其他资源。

### 8.3 运行时适配原则

- 用稳定控件 ID 和后端私有句柄表管理对象，不将自绘控件伪装成 `HWND`。
- 在语言/编译层与 C++ 引擎之间定义窄接口；明确文本编码、字符串与对象所有权、销毁顺序和失效句柄诊断。
- 通过状态表承接“设置属性/读取属性”；适配 `compose` 模型，不在每次界面重组时重建用户对象或重复绑定事件。
- 定义事件派发、重入和回调中销毁窗口的行为；异常转换为现有诊断通道，不跨 ABI 边界传播。
- 明确 UI 线程归属、启动子程序执行时机、主循环归属和最后窗口关闭后的退出条件。
- 多窗口、模态、定时器及停止运行必须有可验证的生命周期，不以“显示了一个窗口”视为接入完成。

### 8.4 编译与分发

- 在 P0 对比“现有工具链编译固定源码”和“消费匹配 SDK”两种方式，选择能与现有公共语言运行时链接的最小方案，并记录决定。
- 检查 C++ ABI、标准库、目标架构、系统 SDK、图形依赖和调试符号；不因上游支持 MSVC/GCC/Clang 就推定内置工具链可直接使用。
- 若现有编译器无法承接，使用已有编译器插件机制补适配，而不是静默切换或宣布所有编译器兼容。
- 按窗口提供者生成程序入口、系统库、平台链接参数和资源部署；EUI Linux/macOS 路径不得继承 Win32 子系统参数。
- 开发期可以受控导入上游；提交必要产物及许可证到仓库内的 `lib/eui/`（拟议目录）。运行时及发布构建只读取仓库随包文件，不依赖开发者外部目录或临时下载。
- 字体、图形着色器及依赖资源纳入打包清单；不得依赖开发机当前目录。
- 开发依赖和终端用户运行依赖分别说明；在干净机器验证缺依赖、无图形设备等失败诊断，不返回成功形状的空结果。

### 8.5 首份独立样例与证据

已新增 [EUI P0 独立样例](../lib/eui-poc/README.md)，固定 EUI-NEO v0.6.3 Windows x64 SDK，使用 MSVC、GLFW + OpenGL。可构建并显示浅深色窗口，含属性/事件、输入框、图片、重置确认以及独立/模态子窗口入口；组件回调测试通过。

真实 Windows 验证目前覆盖主窗口启动、中文与图片显示、浅深色呈现、非构建目录资源加载及主窗口正常退出。真实键鼠、IME、多窗口生命周期、多 DPI 和其他系统尚未完成验收，**P0 整体仍未完成**。

新增已知阻塞：上游 v0.6.3 明确尚未连接系统屏幕阅读器，下载 SDK 也未附单独 LICENSE/NOTICE 文件。正式发布前必须完成系统无障碍桥接和依赖许可核对。样例不注册正式支持库，不改变新建向导或现有项目格式。

### 8.6 Windows 实验接入进度（2026-11-14）

已新增 [EUI 支持库及运行说明](../lib/eui/README.md) 和 [可编辑窗口项目](../examples/eui-window/README.md)，接通提供者贡献点、向导筛选、项目持久化、设计器元数据与稳定控件身份、EUI/MSVC 编译运行。旧项目缺提供者字段仍采用 Win32；缺插件、版本不同或目标不兼容时明确拒绝，不自动切换。

当前仅声明 Windows x64，依赖开发期准备的固定 SDK 和本机 MSVC。Linux/macOS 无候选时阻止创建，不提前默认 EUI。第三方贡献可校验，但未注册执行适配器者不可用；v1 执行目前只开放官方 Win32/EUI。

支持窗口、按钮、编辑框、标签、图片框及属性/事件；原生子窗口销毁重载、图片部署、失败保留旧输出、跳过用户代码的原生预览已有自动化证据。标准 `载入` 只接受显式非模态；`EUI显示窗口` 明确为异步模态，不冒充同步等待语义。

设计器与原生运行时读取同一份主题数据，IDE 主题与项目主题独立；设计器明确标记布局模拟。隔离 Electron 验证键盘新建、实验确认、控件保存重开、不兼容平台拒绝、浅深色背景和按钮文本对比度 ≥ 4.5:1。

验证：typecheck、Electron build、相关 Vitest 5 文件 38/38、隔离 Playwright 1/1；真实 MSVC 编译运行与 Win32 生成快照通过。既有主题契约测试有两条过时源码正则失败，已核对 HEAD 同样不符合，未修改无关旧契约；本次主题行为由隔离 E2E 验证，不宣称全仓库主题门禁通过。

P1 基础已接通，P2 Windows 实验纵向链路已接通，P3 部分完成。系统读屏桥接、完整原生键鼠/IME/多 DPI、完整控件语义、Linux/macOS 及许可分发仍未验收，因此 P0/P3/P4/P5 **不能标为全部完成**。

### 8.7 自绘窗口外壳纠偏（2026-11-14）

初版只统一了自绘控件，运行窗口仍显示 Windows 原生装饰，与设计器模拟的窗口外壳不同。现已改为主/子窗口均取消原生标题栏与非客户区边框，由 EUI 绘制标题、窗口按钮、分隔线、边框与客户区；设计器读取同一份主题数据，不再套用 Win32 外壳。这修正第 1 节“允许原生标题栏差异”的初始选择，保留 Win32 后端、不自动迁移等其他基线。

窗体宽/高保持客户区逻辑尺寸；原生承载高度包含额外自绘标题栏，控件位置从客户区原点计算。Windows 适配只负责拖动、双击最大化、边缘缩放、工作区最大化和窗口生命周期，不负责绘制标题栏/边框。SDK 子窗口没有无装饰配置项，因此在首次可见帧前取消装饰并保留客户区尺寸，不修改固定 SDK 文件。

实测：原生窗口无 `WS_CAPTION`、原生非客户区高度为零；客户区逻辑尺寸、标题/缩放边缘命中测试、自绘按钮键盘最小化/最大化/还原/关闭通过。隔离 Electron 测试核对浅深色标题配色、标题栏高度、按钮宽度与客户区偏移；相关回归 38/38，UI 1/1，类型检查和构建通过。当前是外壳几何与主题一致，不把字体光栅化或所有控件细节称为已达成像素级一致，系统读屏等余项仍保留。

### 8.8 核心与 WebView2 可视控件适配（2026-11-14）

历史实现曾把核心按钮、编辑框、标签、选择框、单选框、滑块条、进度条、分组框、图片框映射为 EUI-NEO 主题控件，并标为 Win32/EUI 双提供者。该处理把窗口提供者与控件来源/实现混为一谈，现按 2026-11-14 修订方案纠正：核心控件按其原生平台适配声明，不再因 EUI 窗口使用而改变控件身份或外观。

`webview2` 浏览框在已实现的 Windows 目标中链接既有实现为真实子窗口，按位置、DPI 缩放、可视性、禁止状态和文本地址同步，并随父窗口销毁；运行需要安装 WebView2 Runtime，设计期地址限 HTTP(S)/`about:blank`。网页按钮与网页编辑框映射 EUI-NEO 主题按钮/输入框，不加载原 HTML 外观。平台支持由各控件实现元数据和窗口宿主能力共同决定。

原有验证证明的是 EUI 仿绘核心控件的实验链路，不作为“Win32 原生控件嵌入 EUI 窗口”的验收证据。后续测试须分别验证控件来源/适配器身份、属性/事件映射、真实原生控件承载及目标平台切换诊断。当前 EUI 和 WebView2 仍仅为 Windows x64 实验适配；不宣称 Linux/macOS 已支持，也未完成系统读屏、完整 IME、多 DPI 与许可分发验收。

### 8.9 控件与窗口提供者解耦、目标平台诊断（2026-11-14）

修订后的实现按以下矩阵计算控件可用性：

```text
可添加 = 控件适配器 ∈ 窗口提供者的宿主适配器
      且 项目目标平台 ∈ 控件已验证目标
```

新建项目工具箱仅展示“可添加”的控件。已放置控件按稳定 `libraryId + typeId` 重新解析；目标变化后即使不再可添加，也要保留在窗体中并显示支持状态。控件库卸载/缺失与目标平台不兼容是不同诊断，均不得删除数据或按名称自动替换。

当前验证范围仅包含仓库内已声明并实现的适配器/目标。窗口支持库无需按控件逐个列出兼容白名单；它实现通用宿主适配器后即可承载所有声明该适配器且目标匹配的控件。平台原生控件只能在真实原生实现/宿主桥接完成后声明支持，不能以 EUI 自绘替代实现冒充原生。

## 9. 设计器、主题与无障碍

### 9.1 设计器

- 保留现有选择、拖放、撤销、对齐、缩放和属性交互。工具箱按目标平台和控件宿主适配器筛选；画布按控件自身适配器预览，不以窗口提供者冒充控件来源。
- 既有控件在当前目标不支持时继续显示，使用主题 token 呈现醒目标记和可访问说明；不能将其从画布或属性/事件面板过滤掉。
- 先支持显式定位，统一客户区原点、逻辑尺寸、DPI 与文本尺寸语义；不能直接重新解释旧项目像素单位。
- 预览描述使用受校验的声明式协议；v1 不为“可插件化”允许任意 React/Node 代码进入渲染器。
- 若先用内置 EUI 预览适配器，须注明这是过渡实现；第三方扩展继续使用既有隔离视图协议，不绕开插件边界。
- 属性说明、分类和默认值来自支持库元数据，不在属性面板新增命令说明或分类语义硬编码。
- 设计期模拟与实际运行预览分别标识；异平台模拟不能标成“目标系统真实预览”。
- 预览与运行使用相同控件语义、布局单位及主题配置；公共语言代码与属性持久化不因预览方式改变。

### 9.2 主题

- IDE 新增选择区、错误提示、占位预览使用现有主题 token/CSS 变量，不硬编码配色、边框、阴影或字体。
- 被设计程序的主题独立于 IDE 主题，不能 IDE 切深色就擅自修改项目外观。
- EUI 运行时采用支持库定义的语义主题 token，并映射到引擎；设计期预览读取同一份配置。
- 同一主题、同一字体资源和同一逻辑尺寸下验证跨平台布局；EUI 窗口外壳使用共享自绘样式，不以原生标题栏差异作为豁免。允许字体栅格化等明确列出的差异，不承诺所有像素完全相同。

### 9.3 无障碍

- 新建流程、提供者选择、错误恢复支持纯键盘操作、清晰标签、焦点反馈和屏幕阅读器语义。
- 自绘控件验证角色、名称、值、焦点、启用状态及键盘操作；不能只验证鼠标或把“画出文本”当成可访问。
- 在 Windows UI Automation、macOS Accessibility、Linux AT-SPI 等目标系统机制下实测；如上游缺少桥接，须补齐或保持实验状态。
- 验证浅深色对比、高对比需求和系统缩放；不得通过删除焦点边框换取外观一致。

## 11. 测试与验收

### 11.1 自动化范围

- 元数据：非法字段、重复 ID、失效 root 类型、缺适配器、API 不兼容、目标/架构交集。
- 项目：新字段读写往返、旧项目不自动改写、保存保留未知字段、缺版本依赖提示、目标平台修改后控件身份/属性保留且出现诊断。
- 创建：零/一/多候选、平台切换、主进程二次验证、取消不落盘、非窗口项目不受影响。
- 控件：同名不同库不冲突、窗口来源与控件来源解耦、工具箱按目标与宿主适配器过滤、既有不兼容控件保留并标记、构建拒绝不支持项、跨后端粘贴拒绝且不损坏原数据。
- 编译：Win32 生成快照保持；EUI 不包含 Win32 入口/链接参数；错误中断、资源正确部署、实际运行生命周期。
- UI：键盘完成新建、选择项可读、错误有语义提示、浅深色主题不越界。

优先扩展现有 [单元测试](../tests/unit/) 和 [UI 测试](../tests/ui/)，复用 [控件生成快照](../tests/unit/controlCodegenSnapshot.spec.ts)、[无障碍测试](../tests/ui/accessibility.spec.js)、[键盘测试](../tests/ui/keyboard-navigation.spec.js)的相关覆盖，不为本方案另建测试框架。

实施后按变更范围先跑相关 Vitest/Playwright 用例，再执行必要的类型、构建与主题检查。现有命令包括 `npm run typecheck`、`npm run build`、`npm run test:theme:gate`；避免每次小改动重复全量测试。

### 11.2 跨平台实测记录要求

每条记录包含：上游 commit、支持库版本、provider API、目标平台/架构、宿主系统、编译器版本、窗口/渲染后端、显示协议、缩放比例、图形环境、执行步骤及结果。

正式支持目标至少验证：

1. 可创建、保存、关闭、重新打开项目，提供者不变。
2. 中文文本、属性读写、事件和窗口销毁正确。
3. 无漏字、截字、控件重叠或点击位置偏移；覆盖 100%、150%、200% 或系统可用的等效逻辑缩放。
4. 键盘、输入法及原生无障碍机制可用。
5. 非工作目录启动及安装包在干净环境运行通过。
6. 无关支持库被安装/停用时，不改变已保存项目的后端和控件解析。
7. X11 与 Wayland 分开记录；未验证的显示协议不笼统宣称支持。

跨平台外观对比采用同一测试窗体、字体、主题、逻辑客户区尺寸和截图条件。布局位置与大小应匹配项目值至多 1 个逻辑单位的取整差；文本不得截断，命中测试位置必须对应视觉位置。字体栅格化和系统装饰差异单独标注，不用任意截图相似度替代功能验收。

### 11.3 初始方案文档的完成标准

初始方案交付只包含本文，不修改项目格式或用户功能；检查文件持久存在、相对链接有效和内容与已核对代码一致即可。后续独立样例的交付和验证见第 8.5 节及样例说明，不能沿用文档验收替代代码构建与运行测试。

## 12. 后续执行纪律

1. 开始某阶段前核对本阶段依赖与退出条件；清单未满足不得宣称该阶段完成。
2. 将能力声明与实测证据绑定，禁止先把三个平台全部写进清单再补测试。
3. 每次实现保持改动聚焦，更新相关测试和直接关联文档；真实功能/修复按仓库规则先记开发日志，再整理用户更新说明。

5. 需要改变“保留 Win32、不自动迁移、单项目单提供者、实验验证后开放”等基线时，先更新本文的变更记录并说明原因，再改实现。
